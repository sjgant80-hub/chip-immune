A defence small enough for a microcontroller.

A signature check, then a settling fit-check, in one fixed block of memory with whole numbers only. It checks its own memory on every input, falls back safely when that memory is corrupted, tries to improve itself in spare cycles with no model, and shares what it learns with other devices over signed messages. Everything here ran on chip-sim, an emulator written to microcontroller rules. It has not run on a real chip yet.

What this is

This is Rung 7, the last rung of a ladder toward computing by geometry instead of by large models. Rungs 1 to 6 tested, each on its own, whether a settling cell can read digits, improve itself with no model, sit behind exact code, share safely, reject shapes that won't settle, and keep working as a fabric loses nodes. Some of that held and some failed, all of it published on the ladder page. Rung 7 asks whether all of that fits the budget of a small device and fails safe there. It is honest about where it stands: the device budget is measured on an emulator, and the run on a real Raspberry Pi is still to come.

Words on this page

Emulator (chip-sim)A program that runs the layer under a microcontroller's rules (fixed memory, whole numbers, bounded loops), on an ordinary computer. It is not a chip; every number from it says so.
ArenaThe one block of memory the layer gets at boot. Everything it holds lives there; nothing is allocated later.
FloorThe first check on every input: the sender's key is on the list, and the Ed25519 signature holds on the raw bytes. Nothing that fails it is ever delivered.
Settle, fitThe layer flips the input's bits one at a time towards its stored digit patterns until nothing more changes. The fit is how strongly the settled state matches them; zero fit means it matches nothing.
AntibodyA stored pattern of a known attack. If the antibodies match the settled state at least as well as the real patterns do, the input is rejected.
CRC-32, down, upA checksum over the layer's memory, checked on every input. If it does not match, the layer is down for that input (the input is delivered, marked unscreened) and reloads from a read-only copy; when that checks, it is up again.
Confirmed attackAn input the device's own application later reports as an attack. A chip has no labels, so this is the only thing it can learn from.
Regression set32 real digits kept on the chip. A self-improvement is kept only if all of them still pass.
SealCommitting the claims (seal 1), then the frozen chip and learning record (seal 2), to the public record before the test digits are read.
Mutation gateA tool (witness) that breaks the code in small ways, one at a time, and checks the tests catch every break. Clean means every one was caught.

How it works

  1. Floor. The input's sender must be on the roster and its Ed25519 signature must hold on the raw bytes, before anything is parsed. A failed floor is never delivered, whatever else is wrong.
  2. Memory check. A CRC-32 over the shape, antibody and energy regions, on every input. If it does not match, the layer reports down, still delivers inputs that passed the floor but marked unscreened, and reloads its regions from the read-only copy, so it is back up for the next input.
  3. Fit-check. The input settles on packed bits exactly as Rung 1's cell settles. Zero fit is rejected as non-fit; if an antibody holds at least the node's fit at the settled state, it is rejected as a known attack; otherwise it passes.
  4. Spare cycles. When the device's own application confirms an input was an attack, it joins a ring of the last 32. The chip tries putting that attack's settled state into an antibody slot, and keeps the change only if it newly rejects a confirmed attack and rejects none of its 32 regression digits.
  5. Share. A device signs its antibody set; another device checks the signature on the raw bytes and runs its own regression check before taking it.

Blueprint

    Adoption

    For a device maker

    A boundary layer that fits the memory of a small device, adds a structural check behind the signature, and never stops the device when it fails. It only gates inputs; it never controls the device.

    For engineering

    One block of memory set aside at boot, whole numbers only, every loop bounded, nothing allocated afterwards. The emulator is the reference to port from; its every result re-derives byte for byte.

    For risk and procurement

    The limits are stated: not yet run on silicon, code size not measured, and no defence against stolen keys, physical tampering or bad firmware.

    A pilot, step by step

    1. Pick one device class and the inputs at its boundary you want gated.
    2. Write down the bars before anything is built, and seal them.
    3. Port chip-sim to C on one development board, and run this record on it. That is CI1, the step not yet done.
    4. Run the layer beside your current input checks, in monitor mode: it reports, it rejects nothing.
    5. Freeze it, then judge it once on inputs it never saw. The fee is due only if it beat your current way.
    6. Only then let it reject inputs, one device group at a time, with the fail-safe in place.

    What the emulator runs on: Node.js 20 or a current browser. A device build would need a C compiler and a C Ed25519 library; neither is measured here.

    White paper: an immune layer for a small device

    The question. Can the settling defence of Rungs 1 to 6 run in a microcontroller's budget, fail safe, improve itself with no model, and share what it learns between devices?

    The method. chip-sim, an emulator held to microcontroller rules, runs Rung 4's defended shape and Rung 5's antibodies. Device A learns from confirmed scrambled training digits; device B adopts A's signed antibodies after its own check. The learning record, shapes and chip code were frozen by hash; then the 10,000 MNIST test digits, held-out attacks and 200 injected faults were run once.

      The limits, plainly:

      • An emulator, not a chip. CI1, a run on a Raspberry Pi, is pending hardware. Timings are estimates from counted operations, not measurements.

      • It gates inputs only. It does not stop a stolen key's genuine-looking inputs, physical tampering or bad firmware.
